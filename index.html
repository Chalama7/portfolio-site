Illustrative request flow

What happens to one request at the edge

Users send requests to edge PoPs in Dallas, Chicago, Ashburn, London and Tokyo. One highlighted request shows the chosen outcome: cache hits are answered at the edge, misses are fetched from an origin that only accepts edge traffic, and blocked requests are answered at the WAF with a 403.

  1. Cache hitTLS ends at the edge, the WAF lets the request through, and the cached copy is returned. The origin is never contacted.
  2. Cache missThe edge forwards the request to the origin, stores the 200 response by cache rules, and returns it to the user through the edge.
  3. Blocked requestA WAF rule matches. The edge answers with a 403 and the request never reaches cache or origin.

Intent-driven CDN prototype

A small engine that turns a desired CDN configuration into reviewable Cloudflare changes, with readback and rollback.

  1. Intent
  2. Snapshot
  3. Diff
  4. Apply plan
  5. Read back
Demonstrated

Against a real Cloudflare zone: applied a configuration, saw a cache MISS then HIT, purged, and saw a MISS again after the purge.

  • Python
  • FastAPI
  • Cloudflare API
Read the case study
Problem
Hand-edited CDN settings drift, and changes are hard to review before they go out or to roll back afterwards.
My contribution
Built on my own, separate from employer work: an intent model with normalization, snapshots, a diff engine, apply plans, DNS state and cache-rule planning, then a FastAPI service with config, purge and health endpoints.
Approach
Describe the desired state, snapshot what is live, compute the difference, apply it as a plan, then read it back. Covers hostname onboarding, TLS, origin checks and simple routing.
Status
Partial working prototype, not production. Components are tested individually.
